# DTO Schema Design Evidence Patterns

Use this reference when closure depends on proving a DTO contract, mapper, generated artifact, consumer compatibility, privacy filtering, or memory/graph claim. Keep the main capability body for routing and selection; load this file only for concrete evidence mapping.

## Claim To Evidence Map

| Claim | Strong evidence | Weak or invalid evidence | Residual risk if absent |
| --- | --- | --- | --- |
| DTO is not an internal model | Source DTO/schema plus mapper/assembler path that allowlists fields | Naming convention only; generated class shape only | Internal model leakage and accidental contract expansion |
| Request rejects unknown fields | Validator or schema test showing undeclared fields fail | A schema file with no runtime enforcement | Mass assignment or object-property authorization bypass |
| Null, absent, empty, and default differ safely | Four-state examples plus mapper/validator tests | A nullable type annotation only | PATCH/mobile/generated-client semantic drift |
| Field type is fit for risk | Money/time/id/enum/file format rule plus boundary test | Plain `number`, `string`, or unconstrained enum | Precision, timezone, identifier, or enum compatibility defect |
| Generated artifacts are fresh | Generator command, generated diff, contract compile/check output | "Generated by CI" without current run or diff | Clients compile or validate against stale schema |
| Consumers remain compatible | Old/new schema diff, consumer inventory, fixture replay or contract test | Caller count from memory only | Hidden mobile, partner, SDK, dashboard, or event consumer breakage |
| Sensitive field is safe | Data classification, allowed-consumer list, redaction/filtering test or denied review | "Not sensitive" with no field review | PII, tenant, object, role, token, or financial exposure |
| Mapper preserves behavior | Source/target field map and tests for old, new, absent, null, invalid, and filtered cases | Snapshot of one happy response | Old DTO fields, validators, or rollback path regress |

## Evidence Labels

- **Strong**: current source path, schema/generator command, contract or validator result, exit code, and fresh artifact after the final edit.
- **Weak**: human statement, stale report, partial fixture, graph-only consumer list, or a test that does not exercise the changed field.
- **Missing**: no current source, no validation command, no consumer search, no generated-client proof, or no privacy decision.
- **Invalid**: evidence from a different DTO, stale generated output after source edit, test that accepts impossible real-world data, or memory claim contradicted by current files.

## Changed DTO To Validation Map

For each changed field, mapper, schema source, generated artifact, consumer class, compatibility path, and privacy rule, record:

```yaml
dto_validation_map:
  dto: ""
  field_or_surface: ""
  change_kind: additive | removal | rename | retype | requiredness | validation | semantic | privacy | generated
  compatibility_class: compatible | conditional | breaking | unknown
  source_paths: []
  consumers_checked: []
  validation:
    command: ""
    exit_code: null
    artifact_or_log: ""
    proves: ""
    does_not_prove: ""
  behavior_preservation: ""
  residual_risk:
    owner: ""
    reason: ""
```

## Closure Checks

- Reject closure if a request DTO changed and unknown-field or allowlisted mapping behavior is not proven.
- Reject closure if a public/generated/mobile/partner/event DTO changed without consumer, generated-artifact, or contract evidence.
- Reject closure if sensitive fields are added or exposed without data classification and denied/filtering proof or an explicit security handoff.
- Downgrade memory, graph, trajectory, and stale report claims unless current source paths and fresh validation confirm them.
