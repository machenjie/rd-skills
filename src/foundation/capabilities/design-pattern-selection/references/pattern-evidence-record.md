# Pattern Force And Coupling Record

- A familiar repository pattern is copied without proving the same force, lifetime, and failure boundary.

Use this evidence pattern to bind one relationship to a current repository force and the obligations it can obscure.

## Decision Record

- Name the current variation, lifecycle, protocol, concurrency, or extension force after structure is accepted.
- Compare a direct call, constructor, function, composition, or existing relationship.
- Name reachable variants, callers, generated consumers, and independent contract boundaries.
- Record creator, owner, dependency direction, invariant boundary, and effect placement.
- Record initialization, synchronization, reset, unsubscribe or drain, shutdown, and failure ownership.
- Keep I/O, latency, timeout, retry, cancellation, cleanup, transaction, and partial failure visible.
- Bound work, queues, backpressure, fairness, cancellation, observation, and saturation.
- Record public, generated, serialized, and cross-module compatibility and deletion paths.

## Claim Limits

- Existing usage proves convention, not current force, lifetime, or failure fit.
- Focused tests prove exercised variants and lifecycle paths, not production load, uninspected consumers, or providers.
- Route placement, API, language, performance, concurrency, and reliability conclusions to their owners.
- Consume the accepted existence decision; do not repeat minimality or placement work.

## Anti-Patterns

- Reject one-variant wrappers, hidden global or I/O work, code-sharing bases, and pattern names without current-force evidence.
